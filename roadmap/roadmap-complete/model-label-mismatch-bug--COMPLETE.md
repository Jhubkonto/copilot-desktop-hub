# Bug: Per-message model label (and actual serving model) changes mid-conversation

Drafted 2026-07-18. **Status: COMPLETE — fixed 2026-07-18.**

`Priority: P1 · Effort: S · Risk: low`

## Resolution (2026-07-18)

Fixed the root cause in `src/main/chat-handlers.ts` (~line 445): `conversations.model` is now
synced **unconditionally** to the latest explicit model override on every send, instead of only
being written while the column was still `NULL`/`'default'`. This keeps the stored model — the
fallback used to resolve and label any message that arrives without its own override — in step
with the desktop picker, so fallback messages (e.g. the Android companion omitting the model) can
no longer be generated by or labelled with a stale model.

Regression coverage added in `src/main/__tests__/chat.test.ts`:
- labels the assistant message with the explicitly selected model;
- syncs `conversations.model` unconditionally (asserts the UPDATE is not gated on `IS NULL`);
- an un-modeled message falls back to the (now correctly-synced) conversation model.

Verified: `npm run typecheck` clean, `npm run lint` clean on changed files, `chat.test.ts` 23/23 pass.

The Android/Kotlin client audit (fix-plan item 2) is rendered moot for the observed symptom by the
main-side sync — the fallback is now always correct even when the client omits the model — but
having the companion always send its current selection remains a nice-to-have follow-up.

## Symptom

In a conversation whose model picker has always been set to `gpt-5.4-mini`, individual assistant responses intermittently show a different model label (e.g. `Model: gpt-5.5`) underneath. Observed on the Android companion UI, but the label originates in the desktop main process. The user never changed the model.

**This is not only a cosmetic label bug** — the label reflects the model that actually served that response. On affected messages the request was genuinely routed to the wrong model.

## Root cause

Each assistant message row stores a `model` column (`messages.model`, migration v5 at `src/main/database-migrations.ts:17`), written by `persistAssistantMessage` (`src/main/chat-handlers.ts:96-118`, INSERT at 114-116) and read back verbatim for Android via `broadcastConversationMessages` (`src/main/chat-handlers.ts:127-137`).

The value persisted is the per-send `selectedModel`, resolved at `src/main/chat-handlers.ts:522-531`:

```
modelOverride (options.model, if not 'default')
  → conversations.model (if not 'default')
  → default_model setting
  → DEFAULT_PROVIDER_MODEL ('gpt-5-mini')
```

Two facts combine into the bug:

1. **`conversations.model` is locked on first send and never re-synced.** `chat-handlers.ts:445-450` only writes it while it is still `NULL`/`'default'`:
   ```sql
   UPDATE conversations SET model = ? WHERE id = ? AND (model IS NULL OR model = 'default')
   ```
   Later picker changes travel only as per-message overrides and never update the row. The only unconditional writer is the `conversation:set-model` WS command (`src/main/ws-handlers.ts:1329-1334`).

2. **The Android send path passes the model through raw and optional.** `chat:send-message` (`src/main/ws-handlers.ts:1217-1289`) does `const model = typeof data.model === 'string' ? data.model : undefined` (`:1220`) and forwards it as `options.model` (`:1279`). Note it forwards `model`, not the `effectiveModel` it computes for CLI routing at `:1251-1256`.

So: the first message locked `conversations.model` to whatever was current then (e.g. `gpt-5.5`). Messages that carry the override resolve to `gpt-5.4-mini`; any message that arrives without `data.model` (or as `'default'`) falls through to the stale `conversations.model` and is generated by and labeled `gpt-5.5`. Result: alternating labels with no user action.

## Latent secondary trap (flag only — not the active cause)

`ProviderNonStreamResult.model?` (`src/main/provider-types.ts:16-20`) is forwarded by the tool loop (`src/main/tool-loop.ts:189-192`, `:356-358`) via `onModel` → `capturedStreamModel`, which takes precedence over `selectedModel` at persist time (`chat-handlers.ts:1302-1306`). **No provider populates this field today** (`sendOpenAIWithTools` at `src/main/providers/openai-provider.ts:254-257`, `sendAnthropicWithTools` at `src/main/providers/anthropic-provider.ts:150`, Azure variants). If anyone later fills it from the API response, labels would silently start showing the provider's resolved snapshot name (e.g. `gpt-5.5-2026xxxx`) instead of the requested id. Add a comment or guard when fixing.

## Fix plan

1. **Keep `conversations.model` in sync with the picker.** When a send carries an explicit model override (`options.model` set and not `'default'`), update `conversations.model` unconditionally instead of only-when-unset (`chat-handlers.ts:445-450`). Then the fallback can never diverge from the last user selection. Alternatively (or additionally), have the clients call the existing `conversation:set-model` path (`ws-handlers.ts:1329-1334`) on every picker change.
2. **Audit the Android client send path** so `chat:send-message` always includes the currently selected model; identify which flow omits `data.model` (regenerate? reconnect? quick-reply?) and close it.
3. **Regression test** in `src/main/__tests__/` covering `selectedModel` resolution: (a) override present → override wins and `conversations.model` is updated; (b) override absent with stale conversation model → resolves to conversation model (pre-fix behavior documented, post-fix should match last selection); (c) fresh conversation, no override → default model.
