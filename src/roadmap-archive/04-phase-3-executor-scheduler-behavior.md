# Phase 3 — Executor & Scheduler-Engine Behavior

Status: **DONE**. Part of the Automated Workflow restructure roadmap — see `00-overview-and-sequencing.md` for how this fits with the other 8 phases. This is the phase where target-hierarchy points 1 and 2 actually get real behavior, not just schema/types.

## Implementation notes

**3a (agent-or-model resolution)**: `agent-turn-runner.ts`'s `AgentTurnOptions.agentId` is now optional; `runAgentTurn` resolves `cfg = agentId ? getAgentConfig(agentId) : null` — no other change needed since the existing generic-system-message/fallbackModel logic already handled a sparse `cfg` gracefully. `automated-workflow-executor.ts`: `resolvePrimaryAgentId` now takes `string | null` and short-circuits to `null` for a null projectId. The old synchronous "no agent → immediate hard-fail" block in `advanceAutomatedWorkflowRun` is **removed entirely** — it's replaced by a three-way resolution (`next.agentId` → primary agent, unless the step explicitly names a `model` → model-mode using `next.model ?? detail.model ?? getAutomatedWorkflowGeneratorModel()`). This turned out to make the old hard-fail case unreachable in ordinary operation (the generator-default model fallback always resolves to *some* model), which is intentional: a step now only ever fails via the pre-existing `runAgentTurn` try/catch (real errors — no provider key configured, API failure, etc.), not via a separate synchronous "no agent" guard. `startActivity`'s `projectId` param takes `detail.projectId ?? undefined` (that type stays `string | undefined`, not widened to accept `null`, to avoid a wider ripple into `BackgroundActivity` for a purely cosmetic conversion).

**3b (scheduler branching)**: `scheduler-engine.ts`'s `executeRun` now dispatches on `task.targetType`; the pre-existing body is preserved verbatim as `executeChatRun`. New `executeWorkflowRun` iterates attached specs in `sort_order`, using `findAutomatedWorkflowRunByScheduleTag` as the idempotency check before creating a new run (via `saveAutomatedWorkflowRunFromSpec` + `setAutomatedWorkflowConfirmationMode` to apply the spec's own `confirmationMode`, then `startAutomatedWorkflowRun`). A **retry of an already-failed spec calls `retryAutomatedWorkflowStep` on its failed step**, rather than recreating the run from scratch — this wasn't fully specified in the original roadmap prose and was decided during implementation as the only sensible way to make a retry actually retry something. Any non-`'done'` status (failure, or a gated pause at `awaiting_confirmation`) stops the batch — a failure throws (for `triggerRun`'s existing backoff/retry loop to catch), a pause just ends the loop and reports `'approval_required'`. `dbListScheduledTaskWorkflows`/`dbSetScheduledTaskWorkflows` (delete-then-reinsert, mirroring `reorderSkillsForAgent`'s precedent) back the attached-specs CRUD; `dbCreateTask`/`dbUpdateTask` thread `target_type`/`workflowSpecs` through.

**Verification result**: `automated-workflow-executor.test.ts` — updated the now-obsolete "fails immediately with no agent" test into a "runs via a bare model" test, added 3 more covering project-less model-mode, explicit step-level model overriding an available primary agent, and confirming the existing explicit-agent path is unchanged. `scheduler-engine.test.ts` — added a new describe block (4 tests) covering multi-spec sequential success, gated-pause batch-stop with `'approval_required'`, in-process retry-without-re-execution (using fake timers to drive the real `triggerRun` backoff loop), and the zero-attached-specs failure case. Full `main` suite: 779/779 passed. Full `renderer` suite: 529/529 passed. TypeScript compiles cleanly project-wide.

## Architectural design choices & reasoning

1. **No changes to `src/main/skills.ts` at all.** This is the single most important design decision in this phase, and it's worth restating why: the target hierarchy's corrected point 1 says skills are *only* available when an agent fulfills a step — never for a bare model, under any circumstances. Earlier drafts of this roadmap proposed extracting a `applySkillConfigsToConfig()` helper to support an "all skills for bare models" mode; that entire code path is now unnecessary and must **not** be built. If a future contributor is tempted to add "just give the model these skills anyway" as a convenience, that's a regression against the corrected design, not a missing feature.
2. **`AgentTurnOptions.agentId` becomes optional, with no new parameters.** The original design considered an `ephemeralSkillIds` option; it's retracted for the same reason as above. The only widening `runAgentTurn` needs is "it's now legal to call this with no agent at all," which it must already support gracefully (generic system message + `fallbackModel`) for a plain bare-model turn.
3. **Resolution order, in words**: an explicit `agentId` wins if present. If absent, and the step didn't explicitly request a bare `model`, fall back to the project's primary agent (today's exact behavior, unchanged). Only if neither an explicit `agentId` nor a resolvable primary agent exists (or the step explicitly asked for a `model`) does the step run in model-mode. This ordering is deliberately conservative — it changes nothing about any step that already resolves to a real agent today; it only adds a new fallback branch for cases that would otherwise hard-fail.
4. **Why this is where the project-optional change from Phase 1 and the corrected point 1 "compose"**: `resolvePrimaryAgentId(projectId)` returns `null` when `projectId` is `null` — there's no `project_agents` row to look up for a project that doesn't exist. So a project-less run has zero agent fallback, and any step in it that doesn't explicitly name an agent falls straight into model-mode (no skills). This is a real, load-bearing interaction between two separate phases' changes, not a coincidence — call it out explicitly in code review when this phase lands, since it's easy to miss that "project-less" and "no-skills-by-default" are the same underlying mechanism from two different angles.
5. **The hard-fail gate gets *strictly narrower*, not more permissive in a risky way.** Today, a step fails if no agent can be resolved at all. After this phase, a step fails only if it has neither an explicit `agentId`/`model` nor a resolvable primary agent — i.e., today's failure cases still fail exactly as before; the only new success case is the model-mode fallback. Write the regression test for this explicitly (see Verification) so a future change can't silently widen the gate further without a test catching it.
6. **Scheduler branching keeps the existing `dispatchChatSend` path completely untouched.** `executeRun` splits into `'chat'` (today's exact behavior, unmodified) and a new `executeWorkflowRun` for `'automated_workflow'`. This isolation means Phase 3 cannot introduce a regression in the plain-chat scheduling path that predates this entire roadmap — the new code is additive and orthogonal.
7. **Multiple attached workflows run sequentially, not in parallel.** This matches the engine's existing one-active-run-per-task philosophy (`triggerRun` already enforces one active run per task) and keeps failure semantics simple: the first failure in the sequence stops the batch, rather than needing to reconcile partial-parallel-failure states.
8. **Retry-idempotency**: a retried `scheduled_runs` row must not re-run workflow specs that already completed under an earlier attempt of the same run. This is exactly what Phase 1's `automated_workflow_runs.scheduled_run_id`/`spec_sort_order` columns are for — before starting spec N, check whether a run already exists tagged with this `scheduled_run_id`/`spec_sort_order` pair, and skip it if so.
9. **Final schedule-run status of `'approval_required'`, not `'failed'`, when a spawned workflow is gated and awaiting confirmation.** `scheduled_runs.status` has included `'approval_required'` in its CHECK constraint since migration 39, but nothing has ever produced that value — it was seemingly anticipated for exactly this kind of case and never wired up. Repurposing it here is more correct than either `'failed'` (it didn't fail, it's waiting) or `'success'` (it isn't done yet).

Persist `workflow_run_ids_json` with every spawned run's id.
