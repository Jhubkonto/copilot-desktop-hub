# Code Changes Compatibility (Historical)

> Removed in schema version 89. This document is retained only as implementation history; the Git code panel remains supported independently.

## Current architecture

`Code Changes` is the user-facing product model. The first migration keeps the established remote-edit implementation as internal plumbing:

- SQLite records remain in `error_reports`.
- Desktop IPC channels remain under `error-report:*` and `remote-edit:*`.
- Android WebSocket commands remain under `error-report:*` and `self-heal:*`.
- Staging, diff, verification, git, and history tables retain their existing names.

These identifiers are implementation details and must not be used as user-facing labels.

## Request metadata

New records persist neutral metadata directly on `error_reports`:

- `request_type`: `edit`, `refactor`, `bugfix`, `feature`, `investigation`, or `custom`
- `custom_type_label`: free-text label, set only when `request_type` is `custom` (migration 47)
- `request_origin`: `chat`, `android`, `manual`, `build-failure`, or `legacy-bug-report`
- `workspace_root`: workspace targeted when the request was created
- `project_id`: optional originating Nexy project

Rows created before migration 46 have null metadata. The shared compatibility adapter presents those rows as:

- type: `edit`
- origin: `legacy-bug-report`
- workspace: current connected workspace when no stored workspace is available

No destructive data migration is required, and existing request IDs continue to work with investigation, staged patch, verification, and git operations.

## Safety boundary

The backend still executes against the current desktop `build_workspace_path`. The stored `workspace_root` is provenance, not authorization to edit a historical path. The Code Changes UI therefore shows and validates the current connected workspace before allowing new requests.

Android is a remote review/control surface. It displays the connected desktop workspace but does not independently select a filesystem path — all filesystem access happens on the desktop, driven by commands received over the WS protocol.

**Update:** the earlier assumption that Android remains view-only for apply/verify/commit is superseded. Android now supports the full Code Changes lifecycle end-to-end: create, investigate, review a staged patch, delete, apply to workspace, run verification, push, and trigger recovery/rollback. Planning/backend settings (model, backend, retry limit, auto-approve tools) are also configurable from Android now — see "Planning settings sync" below. What's still desktop-only:

- Workspace/repo selection (the folder picker that binds `build_workspace_path`).
- Git prepare/commit UI (Android can push an already-committed change via `self-heal:git-push`, but composing and creating the commit itself is desktop-only in this pass).
- Anything else requiring direct local filesystem access outside the WS protocol.

### New WS commands

Two commands were added to the existing `self-heal:*` namespace so Android can reach parity without introducing a new namespace:

- `self-heal:delete-report` — deletes a change request (mirrors the existing `error-report:delete` IPC handler's `deleteErrorReport()`). Broadcasts `self-heal:report-deleted` with `{ reportId, deleted, error? }` — success/failure is always unambiguous, never inferred from a falsy value.
- `self-heal:apply-staged-patch` — applies the staged patch to the connected workspace (mirrors the existing `remote-edit:commit-to-workspace` IPC handler; both now call a shared `applyStagedPatchToWorkspace()` function in `remote-edit-handlers.ts` to avoid duplicated apply logic). Replies with `self-heal:apply-result` carrying `{ reportId, appliedFiles, backupPaths }` on success or `{ reportId, error }` on failure.
- `self-heal:get-investigation-settings` / `self-heal:set-investigation-settings` — mirrors the existing `remote-edit:get-investigation-settings` / `remote-edit:set-investigation-settings` IPC handlers (both call the same `loadInvestigationSettings()` / `saveInvestigationSettings()` in `investigator.ts`, so desktop and Android always read/write the same stored settings, not per-platform copies). Reply/broadcast event is `self-heal:investigation-settings` with `{ backend, model, retryLimit, autoApproveTools }`.

All other commands Android needs (`self-heal:start-verification`, `self-heal:git-push`, `self-heal:get-recovery-runs`, `self-heal:start-reload`, `self-heal:approve-relaunch`, `self-heal:request-rollback`) already existed server-side before this work — only Android's client-side plumbing (WsEvent types, WsRepository functions, ViewModel state, UI) was missing.

### Planning settings sync

Android's `RemoteEditReportDetailScreen` shows a collapsible "Planning settings" card (backend, model, retries, auto-approve tools) above the plan/retry action, visible whenever a request hasn't been planned yet or a plan attempt failed — the same visibility rule desktop uses. This closes a gap where a phone-only user who hit "No provider configured" during planning had no way to fix it without opening the desktop app, since there was previously no WS surface for investigation settings at all. Saving from Android calls `self-heal:set-investigation-settings`, which persists to the same `settings` table rows desktop reads from — there is one shared configuration, not independent per-platform state.

### Shared phase model

`CodeChangeRequestPhase` / `CODE_CHANGE_PHASE_LABELS` / `CODE_CHANGE_PHASE_GUIDANCE` / `deriveCodeChangePhase()` (`src/shared/code-changes.ts`) are ported field-for-field to Kotlin in `android/app/src/main/java/io/nexy/android/data/model/CodeChangePhase.kt`, replacing an earlier ad hoc `presentationPhase()` function that lived in `RemoteEditReportsScreen.kt` and didn't take verification/commit state into account. A JUnit fixture test (`CodeChangePhaseFixtureTest`) guards against the two implementations drifting apart — update both together when the phase-derivation logic changes.

### Navigation

Code Changes moved from Android's Settings → Developer section to a dedicated top-app-bar icon on the Home screen (`onOpenCodeChanges`, next to the Artifacts icon), matching the prominence of desktop's sidebar entry. The Settings entry was removed entirely — there is exactly one canonical entry point now. The chat-prefill deep link (`remote-edit/start?prefill=...`) is unaffected since it navigates directly to the route.

## Deprecated behavior

Crash reporting is separate from Code Changes and no longer creates or opens a repair workflow automatically. Recovery/reload APIs remain registered for compatibility with old in-progress runs, but are not part of the primary Code Changes product flow.

Internal channel and table renaming should be handled as a separate migration only when all supported desktop and Android versions can be upgraded together.

## UX overhaul (post-parity)

A follow-up pass addressed usability issues that surfaced once Code Changes was a general-purpose, cross-platform feature rather than an internal self-heal tool:

- **Debug logging**: the app-wide debug logging toggle was relocated from the Code Changes modal to Settings → Developer → Console. It was never a Code Changes concept.
- **Request taxonomy**: `feature` and `custom` request types were added (migration 47 widens the `request_type` CHECK constraint and adds `custom_type_label`). Android gained request-type selection UI for the first time (previously hardcoded to `edit` server-side for Android-originated requests).
- **Chat-driven creation**: desktop's "Create code change" action from chat no longer creates the request immediately. It now seeds a `pendingNewRequestDraft` (`uiSlice.ts`) that pre-fills the existing new-request form for review/edit before the user explicitly confirms — matching the review step Android's `RemoteEditStartScreen` already had.
- **Workspace confirmation**: the request review form and detail view now make the targeted workspace explicit rather than silently applying the globally-connected build workspace. A warning banner appears in the detail view when a request's stored `workspace_root` no longer matches the live connected workspace (warn-only; the backend still executes against whatever is currently connected).
- **Undo, not reload**: the post-verification "Prepare reload / Package for reload / Relaunch now / Rollback" flow — meaningful only for the original self-heal case of patching and relaunching Nexy itself — was collapsed into a single "Undo this change" action backed by `rollbackHeal()`. The desktop main process now silently calls `prepareReload()` (captures the backup manifest) the moment verification succeeds, so no separate "prepare" step is user-visible. `rollbackHeal()`'s status guard was relaxed to accept `'prepared'` directly. `startReload()`/`approveRelaunch()` remain registered but have no UI entry point in Code Changes on either platform.
- **Guided, staged presentation (desktop)**: `RemoteEditPanel.tsx` no longer renders every section (workspace banner, new-request form, list, detail, history) unconditionally in one scrolling modal. It now switches on a single `view` mode (`list` / `new-request` / `detail` / `history`), matching the screen-per-step structure Android already had via Compose Navigation. Within `detail`, sections are gated by the request's phase: the current phase is expanded, completed phases collapse into a one-line summary (click to re-expand), and future phases aren't rendered at all.
- **"Investigating" → "Planning"**: phase labels, guidance text, and button copy ("Analyse" → "Plan") were renamed on both platforms to drop self-heal-era bug-diagnosis language that didn't fit general edit/feature/refactor requests. The phase *id* (`'investigating'`), DB columns, and IPC/WS channel names are unchanged — this was a presentation-only rename, guarded by the existing `CodeChangePhaseFixtureTest` drift check.
- **Planning settings dead end fixed**: `deriveCodeChangePhase()` incorrectly reported the `investigating` phase for a request whose plan had just failed, because a failed attempt still populates `investigation_markdown` (with the failure doc) even though `status` reverts to `'open'` for retry. This hid the phase-gated planning-settings UI and the retry action on both platforms, leaving a user who hit "No provider configured" with no visible way to fix it. Fixed by checking `investigation_root_cause === 'investigation_failed'` explicitly in the phase derivation (shared by both platforms) so the phase correctly reverts to `draft`.
- **Live planning progress**: previously the only visible feedback during a plan run was a "Planning..." button label — the activity feed and streaming output existed in state but stayed hidden until content had already arrived, leaving a dead gap right after clicking. Both platforms now show a spinner/"Starting..." placeholder the instant a run begins, and the activity/output panel is visible immediately rather than gated behind "has content arrived yet." Retrying a failed plan also now clears the previous attempt's stale activity log instead of carrying it over. Because investigation/planning happens in the main process independent of any renderer window, closing the desktop modal (or navigating away on Android) does not stop the run — both platforms now detect a request whose DB `status` is still `'investigating'` with no local activity recorded (i.e. it was started before this screen/window was opened) and show a "Planning is still running in the background" indicator with the action button disabled, rather than looking like nothing has happened.
- **Plan review gate restored**: `persistResult()` in `investigator.ts` previously set `error_reports.status` straight to `'investigated'` the instant a plan finished streaming, with no human checkpoint in between — the app treated "the AI call returned" as equivalent to "the plan is approved." This meant a plan that identified zero affected files (a real, not-uncommon outcome — the model may find nothing actionable, or its output front matter fails to parse) sailed through identically to a good plan, and the Accept/Reject/Revise UI that was already built for review (`CodeChangeInvestigationSection.tsx`, gated on `status === 'investigating'`) was unreachable dead code, since status had already moved past that value by the time the user saw the result. Fixed by leaving `status` at `'investigating'` when a plan completes; only the explicit Accept action (`remote-edit:set-report-status` / `self-heal:set-report-status`) now advances it to `'investigated'`, which is what actually unlocks "Generate staged patch." `deriveCodeChangePhase()` needed no change — it already mapped `status === 'investigating'` (with markdown present) to the "Planning" phase and `status === 'investigated'` to "Patch ready," so the phase stepper now correctly reflects the review gate. Android gained a `self-heal:set-report-status` WS command (previously accept/reject only existed as a desktop IPC handler) and its own Accept/Reject/Revise row, plus an amber warning that disables Accept when the plan's `affected_files` list is empty. Both platforms also now always render the full plan body (not just its YAML front matter) so the user can see what the AI actually said before deciding.
- **Undo reachable after a failed verification**: "Undo this change" was nested inside the verification-*passed* success block on desktop, so a request stuck at `needs-attention` after verification failed had no undo path at all, even though the patch had genuinely already been applied to the workspace (with backups saved). The underlying `prepareReload()` (`recovery.ts`) — which captures the backup manifest the undo action restores from — independently *also* refused to run unless the latest verification had passed and the git workspace was clean, requirements inherited from the original self-heal reload/relaunch flow that don't apply to a pure file restore. Fixed on both fronts: `prepareReload()` now only requires `fix_status === 'applied'` and a non-empty backup manifest; the desktop main process calls it after every verification run regardless of outcome (previously success-only), so a recovery run always exists once a patch has been verified at all; and "Undo this change" is now a standalone action shown whenever `fix_status === 'applied'`, not nested under a successful verification. A "Revise plan" action was also added next to "Revise patch"/"Re-run verification" in the verification-failed block on both platforms, since regenerating the patch alone can't fix a plan that was the actual problem. `startReload()`/`approveRelaunch()` (the vestigial relaunch flow this guard was originally written for) are unaffected — they have no UI entry point in Code Changes and independently check their own recovery-run status before acting.
- **Clickable phase navigation**: the phase stepper badges (Draft/Planning/Patch ready/Applied/Verifying/Ready to commit/Committed) were purely decorative — no click handler, no visual affordance suggesting interactivity, and no way to jump back to an earlier phase's content once later phases had been reached. Fixed by making each badge in `PhaseBar` (`primitives.tsx`) clickable once its phase has been reached (an `onStepClick` callback, cursor/hover styling only applied to reachable steps), and restructuring `RemoteEditDiffViewer` from one monolithic block into four independently collapsible `PhaseSection`s (`patch-ready`, `applied`, `ready-to-commit`, `committed`, each with a stable DOM `id`) so a badge click can expand-and-scroll to the specific section that phase's content lives in, rather than one merged block covering five different phases. A "Planning" click similarly expands and scrolls to the plan-review section. Previously-reached phases now stay visible as their own section (defaulting expanded, independently collapsible) instead of being folded into a single "Patch applied to workspace" summary — this also surfaces a "Committed" confirmation section that didn't exist before. Android had no phase stepper at all (just a plain "Phase: X" text label) — added a tappable `PhaseStepper` composable mirroring desktop's colored-pill design, using `onGloballyPositioned` to record each section's scroll offset and `ScrollState.animateScrollTo()` to jump to it on tap.
- **Spacing/polish pass (desktop)**: the collapsible plan/phase sections (`CollapsibleStep`, `CodeChangeInvestigationSection`) rendered their children with zero gap between them (e.g. the "Hide plan" toggle sat flush against the "no affected files" warning box below it), and the detail view's header row blended into the phase-bar/guidance banners above it with uniform spacing regardless of grouping. Fixed by adding `space-y-2`/`space-y-3` wrappers inside each collapsible section's content and a `border-t` divider above the request title/description row.
- **Background-run visibility**: a request actively planning (or later, staging/applying a patch) gave no visual cue in the request list — the row showed only a static phase label, indistinguishable from an idle request, so navigating back from the detail view while a run was in progress looked like nothing was happening. Fixed by showing a spinner + "Working…" label on the busy row in `CodeChangeListView` (reusing the existing `isReportBusy` check). Extended further to the app-wide sidebar: the "Code Changes" nav button now shows a small spinner whenever any request has `status === 'investigating'` or `fix_status` in `('staging', 'applying')` — derived from the same polled `listErrorReports` call already used for the open-request badge count, with the poll interval tightened from 30s to 4s while something is running, so the indicator stays visible even when the Code Changes modal is closed.
- **"Revise" actually revises now**: the "Revise" / "Revise plan" actions (plan review, failed-patch-generation recovery, failed-verification recovery) previously just called `startInvestigation()` again with no way for the user to say what was wrong — functionally identical to a blind retry, discarding any diagnosis the user had just made when looking at an empty or wrong plan. Fixed end-to-end: `buildPrompt()` in `investigator.ts` now accepts optional `revisionNotes` and, when present, appends a "the previous plan was reviewed and needs revision" section with the user's guidance verbatim; `runInvestigation()`, the `remote-edit:start-investigation` IPC handler, the `self-heal:start-investigation` WS command, and `window.api.startInvestigation()` all thread an optional notes string through end to end. Both platforms replaced the bare "Revise"/"Revise plan" buttons (three call sites each — plan review, patch-generation failure, verification failure) with a shared `RevisePlanControl` (`RevisePlanControl.tsx` on desktop, a private composable of the same name in `RemoteEditReportDetailScreen.kt` on Android) that expands into a short text field ("What should the plan do differently?") before submitting, rather than firing immediately on click. Notes are not persisted — they're passed through for that one retry only, matching how a plan retry has always been an ephemeral, one-off action.
- **List row busy state didn't survive a modal remount**: the newly-added list-row spinner (see "Background-run visibility" above) was gated solely on `RemoteEditPanel`'s local `runningReportId`/`fixRunning` state, which resets to `null` every time the panel remounts — e.g. closing and reopening the Code Changes modal while a plan is running in the main process. The sidebar's independent, DB-polled "something is running" indicator would correctly keep spinning, while the request's own row in the list (freshly loaded from the DB, showing the true `status: 'investigating'`) rendered as if idle, because the busy check only asked "did *this session* start a run?" not "does the DB say a run is in progress?" Fixed by having `CodeChangeListView`'s busy check also treat `report.status === 'investigating'` and `fix_status` in `('staging', 'applying')` as busy, matching the same DB-derived signal the sidebar already used. Also added a 4-second polling refresh of `reports` while the list view is on screen (previously `reports` only reloaded on modal mount/explicit actions, so a row could sit stale — phase label frozen, busy indicator gone — until the user manually hit "Refresh" or navigated away and back).
- **Reworked to be project-scoped (desktop)**: Code Changes was a standalone sidebar modal (`RemoteEditPanel.tsx`) bound to one global "connected workspace" (`build_workspace_path` setting) — disconnected from Projects, which already had a well-defined `rootDirectory` and auto-detected git/workspace metadata (`ProjectConfig.workspaceInfo`). Reworked to be triggered from within a project instead: a new "Code Changes" tab (id `code-changes`, distinct from the pre-existing "Changes" tab/`AuditTab.tsx`, an unrelated read-only audit log of agent-touched files) was added to `ProjectSettingsPanel.tsx`, hosted by a new `ProjectCodeChangesTab.tsx` that ports the same view-mode state machine and list/detail/diff components essentially unchanged, but derives its workspace from `projectConfig.rootDirectory`/`workspaceInfo` instead of a global setting. The standalone modal, its sidebar entry point, and `showRemoteEditPanel` store state were removed entirely. Main-process workspace resolution became per-report: `getWorkspacePath()` (global) was replaced by `getWorkspacePathForReport(reportId)` in `investigator.ts`, which resolves via the report's linked `project_id` → that project's *current* `rootDirectory` (so a project's root directory can be edited later and every action against its requests follows), falling back to the report's own `workspace_root` snapshot (for the build-failure origin, which isn't project-scoped) and finally to `process.cwd()`. Every call site across `fix-agent.ts`/`verifier.ts`/`recovery.ts`/`git-ops.ts`/`remote-edit-handlers.ts` already had `reportId` in scope, so this was a like-for-like swap; `git-ops.ts`'s internal `git()` helper lost its default-parameter global-workspace fallback and now requires an explicit `cwd`. The desktop build/package feature's own separate `getWorkspacePath(db)` in `build-handlers.ts` (same setting key, unrelated feature) was untouched. Since every existing Code Changes request in the database was test data, migration 50 does a one-time `DELETE` of `error_reports` and its dependent tables rather than backfilling `project_id` onto old rows — there is no "unlinked requests" view; a request only gets created going forward if it resolves to a project (via the tab it's created from, or via server-side `inferProjectIdForWorkspace()` inference for the build-failure entry point, which now only proceeds if a project match is found). Chat's "Create Code Change" action navigates straight to the resolved project's Code Changes tab; when no project is active for the chat, the action is shown disabled with a tooltip rather than hidden or offering a project picker. Android is unaffected — it has no Project concept yet, so its WS-based request creation still doesn't set `project_id`, a known, accepted gap for a future pass.
- **Planning prompt was bug-diagnosis language for every request type**: `buildPrompt()` in `investigator.ts` unconditionally told the model "Investigate the captured bug," required a `root_cause` field, and instructed it to ground every claim in the log snapshot and ignore anything outside "this bug report" — regardless of the request's actual `request_type` (`edit`/`refactor`/`feature`/`custom` all got the same bug-hunting framing as `bugfix`). For a refactor/feature/edit request there is usually no relevant log snapshot and no bug to find, so the model correctly (given the prompt it was sent) concluded nothing was wrong and returned `affected_files: []` — which then correctly blocked Accept (a plan with no files can't produce a patch), but the actual problem was the investigation being pointed at the wrong task entirely, not the Accept gate. Fixed by branching the system/user prompt on `request_type`: `bugfix`/`investigation` (and null/undefined, matching the existing default-to-bugfix convention elsewhere in `code-changes.ts`) keep the original "investigate the bug, ground claims in the log snapshot" framing; every other type gets "Plan this change request," instructions to ground claims in the files actually read via tool calls instead of a log snapshot, and the `root_cause` YAML key (kept as the same field name — the parser and `investigation_root_cause` column are unchanged) is described to the model as "a one-sentence summary of the planned approach" rather than "a one-sentence root cause."
- **Tool-incapable OpenRouter models silently produced empty plans**: `investigator.ts`'s BYOK planning path always sent a native `tools` payload to whatever model was configured, with no capability check. Some OpenRouter models (Hermes/Nous-family in particular) accept a `tools` payload without erroring but never populate a structured tool-call response — they emit their own pretrained pseudo-tool-call text (e.g. a literal `<tool_call>...</tool_call>` block) as plain content instead, which the native tool loop can't parse. The only existing safety net was a reactive fallback to a prompted (JSON-in-text) tool-calling mode, triggered solely by the specific error message `"No endpoints found that support tool use"` — but OpenRouter didn't reject the request for Hermes, so that fallback never fired, and the investigation silently ran with zero usable tool calls, producing `confidence: unknown` / `root_cause: unknown` / `affected_files: []` regardless of request type. Fixed by extracting the OpenRouter tool-capability heuristic that chat dispatch (`chat-provider-dispatch.ts`) already had (catalog lookup, falling back to a known-tool-capable-family allowlist for models with no catalog entry) into a shared `resolveToolsSupported()` (`src/shared/models.ts`), and having `investigator.ts` check it *before* the first call — routing straight to the prompted tool-calling path for models like Hermes instead of waiting for a rejection that may never come. `chat-provider-dispatch.ts` now delegates to the same shared function instead of duplicating the heuristic inline.
- **No way to switch models before revising a plan**: desktop's `RevisePlanControl.tsx` gained an inline model picker (`reviseModelPicker`, `ProjectCodeChangesTab.tsx`) so a user whose plan came back wrong because of a weak model didn't have to leave the revise flow to fix it — picking a model there updates `investigationSettings.model`/`backend` and persists it (`persistInvestigationSettings()`) immediately before the revision's `startInvestigation()` call. Android's `RevisePlanControl` composable (`RemoteEditReportDetailScreen.kt`) initially had no equivalent, and unlike desktop, Android's separate "Planning settings" card is only shown pre-plan or after a failed *planning* attempt — not after a *rejected* plan — so an Android user revising a rejected plan had no way to change the model at all. Fixed by giving `RevisePlanControl` an optional `investigationSettings`/`onSaveInvestigationSettings` pair, rendering a compact "Model for this revision" field (pre-filled from the current settings) above the notes field when provided, and saving via the existing `vm.saveInvestigationSettings()` → `self-heal:set-investigation-settings` path — the same shared `settings` row desktop's picker writes to — immediately before firing the revision. All three call sites (plan review, patch-generation failure, verification failure) now pass it through, matching desktop's three call sites.
